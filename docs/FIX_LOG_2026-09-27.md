### 17.1 指引 chip 显示被作废的上一版（critical）
- 现象：chip 显示 Meta `$125–145B（↑自 $115–135B）`，而下方表格 7/29 行写着 130 / 145。页面自相矛盾。

## 19. 2026-09-28 定时任务失败：滚动窗口导致的测试脆弱（非数据故障）

**现象**：`36381463851` 在 05:20 失败于测试门，页面未更新（线上仍是上一轮成功构建）。

**根因**：每日任务用 `--start-date = 今天 − 370 天`。09-28 减 370 天 = **2025-09-23**，
370 天滚动窗口已把 **2025-09-22 那个残周滚出数据之外**，底表首周变成完整周 2025-09-29。
而 §18.3 写的断言硬编码了"残周一定是底表首周、且一定被剔除"：

```
assert str(raw_weeks[0]["date"]) == snapshot["meta"]["volumePartialWeekDropped"]
AssertionError: assert '2025-09-29' == None
```

这是**测试假设过期**，不是数据或构建缺陷。残周只在它还落在 370 天窗口内时存在——
窗口一旦滚过它，残周检测本就不该触发。生产代码行为完全正确。

**修法**：断言改为状态无关——
- 有残周：必须被剔除，且剔除的正是底表首周（`dropped not in dates`）
- 无残周：图上首周必须就是底表首周（`dropped is None`）
两种状态各自锁死，窗口滚动不会再误报。

**验证**：两种状态各跑全量 83 项，均通过；另合成验证 Demand 时钟在 52 个完整周时自动回到 `Trend`
（即 §18.3 所说的"下个采集周期自动恢复"逻辑成立）。

**教训**（已写入 CONTEXT.md）：滚动窗口类指标（周数、窗口起点）在测试里不得硬编码具体周数，
必须由 `week_quality.py` 的共享尺子推导。数据自然增长/滚动时，硬编码断言必然在某个时点集体过期。
