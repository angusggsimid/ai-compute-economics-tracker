## 1. GPU Finder API 全量调研结论（指导采集设计的硬事实）

- 计费：每次成功调用 = 1 单位（无论返回多大；上限 10,000 行 / 2 MiB / 10 秒，超限失败仍计费）；每次重试另计；鉴权/参数校验失败不计费；`/usage` 免费（随时可查余量）；`/status` 计 1 次。
- 接口广度（7 个数据接口，均单 GPU/次）：
  - `/availability?gpu=`：**7 天滚动窗口、逐日 cells**（provider × 节点规格的 available/total）——全部接口里唯一"单次跨度大"的数据；参数只有 gpu/provider，无法延展窗口；
  - `/snapshot?gpu=&count=节点卡数`：只有"当下"（挂牌/在库分开，含整机与单卡时价）；**无历史可回补**；
  - `/prices` 当下整机价；`/history` **月度** per-provider 地板价（REST 3 年截断）；
  - `count` 参数是**节点加速卡数（1–10,000）**、不是返回条数——无法一次调用拿多个 GPU。
- 上游数据节奏：价格每日、库存每小时（21 家 provider API）；官方的 Availability Index 研究数据集是**月度聚合**（reliabilityPct/coverage 等），无逐日序列，不能替代采集。
- 结论：稀缺度/广度可低频但**日密**（靠 7 天窗口）；报价虚低度密度=采集频率，额度内上限约 2.5–3 天一轮。

## 2. 静默数据丢失：滚动窗口回写整行覆盖（已修）

- 现象（复盘历史提交确认）：gap（价差）与 providerCount（家数）**每个提交里都只剩最后一天有值**（连续 3 个提交均如此）。页面后果：报价虚低度图长期停留在 KPI 数字（gapValidDays=1<10），广度图几乎空白。
- 根因：`_merge_daily` 按 (date, gpu) **整行覆盖**。"回补的 7 天窗口历史行"只带可用率字段，却把同一日期此前已抓到的价格/家数字段整行抹掉；窗口滚过 7 天后该日数据永久只剩可用率。
- 修复：改为**字段级合并**——本轮抓到的字段覆盖、未抓到的保留；显式 None 如实覆盖（"今日无在库报价"是事实）；快照成功但价差不可计算时清掉旧价差、清掉旧错误。
- 验证：新增 2 项回归测试（窗口回写保字段 / 显式 None 赢且清旧价差）。

## 4. 采集轨道化（60 次/月额度内的最优分配）

- availability：**≤6 天一轮**（7 天窗口 → 逐日零丢失）≈ 5 轮 × 3 = 15 次/月；
- snapshot：**~2.5 天一轮**（受日程粒度影响实际约 3 天）≈ 10 轮 × 3 = 30 次/月；
- history：~28 天（3 次/月）；catalog：~30 天（1 次/月）；
- 合计 ≈ **49 次/月**，留 ~11 次重试/手动验证余量；未到期日**零请求**跳过（输出 current_for_frequency）。
- 新增 `cadence`（各轨道上次成功时间，旧格式自动迁移）与 `--dry-run`；`--force` / 云端 `force_gpufinder` 仍可全量重扫。
- 验证：本地 dry-run / 跳过路径零请求；全量 130 项测试通过；本地构建产出：稀缺度 **60 点/20 天**、广度 **60 点/20 天**、虚低度开始积累（KPI 模式，≥10 个收集日后转正式线图）。
